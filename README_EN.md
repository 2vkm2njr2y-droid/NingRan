# NingRan Encryption

[中文](README.md) | **English**

NingRan Encryption is a local file-protection application for Windows x64. File encryption, decryption, identity management, and device verification are performed on the local computer. The application does not intentionally upload files, passwords, key files, or identity data.

> Current build version: **9.0.1**. The Windows x64 installer is generated in the repository's `dist` directory.

## Features

- Encrypt and decrypt files or folders.
- Use **Secure Delivery** to combine multiple files and folders into one `.nrenc` package with expiry, recipient, and plaintext-export rules.
- Choose from the three legacy protection modes or the new flexible combination mode.
- Flexible mode can require any combination of password, key file, continuously detectable removable storage keys, and Windows Hello. Every selected condition must pass. Physical rules support a minimum number of inserted keys and a forbidden-device list; the session is cancelled when the rules stop being satisfied.
- Optionally create a dual-space fixed-capacity vault; two different passwords open independent contents through the same entry point.
- Browse unlocked encrypted-file trees in the application. Common text, image, audio, and video files are read on demand without leaving plaintext on disk.
- Use the embedded secure media player with a file list, full screen, left/right seek keys, click-or-drag seeking, and timeline hover previews.
- Create, back up, and restore private identities.
- Share public identities and verify contacts with a case-sensitive seven-letter security code.
- Hide the protection method, original names, internal directory structure, sender, and device information until successful unlock.
- Keep one main window per Windows user. Opening the application or an associated file again forwards the new file to the existing window.
- Use Strict Protection, which runs a separate administrator-approved monitor that periodically checks the main window, embedded player, preview surface, and the monitor itself, then stops work and cleans temporary content after detecting suspicious access.

## File Types

- `.jpg`: NingRan encrypted photo created on an NTFS disk by version 7.0 and later. The file itself is an ordinary JPEG, so ordinary viewers show the user-selected cover. Encrypted content is kept in the file's NTFS alternate data stream.
- `.nrenc`: portable NingRan encrypted package and the default output format on non-NTFS disks. Version 9.0.1 continues to read `.nrenc` files from 8.0.1, 8.0.2, 8.0.5, and the legacy 6.1 format. For ordinary (non-delivery) packages, appending or removing items adds an encrypted tail segment instead of building a full temporary copy; removals take effect in the newest directory, so an update no longer needs free space for a second copy of the whole archive.
- `.nrkey`: Dedicated key file generated by the application.

### Flexible protection and Windows Hello

The new format uses an independent `NRARC009` header. Existing archives remain readable under their original rules and are not rewritten automatically. A new archive can require any combination of password, key file, physical keys, and Windows Hello; every selected condition is required. A key file can be used by itself or combined with other conditions. Physical protection can require a minimum number of removable storage keys and can reject a forbidden registered device. The session keeps checking the device rules and cancels the current view or write operation if they are no longer satisfied.

Windows Hello credentials are bound to the computer and Windows account used during registration. Configurations that support HMAC-secret/PRF use the Hello-derived offline secret directly; configurations without that optional extension use a local recovery secret still protected by the current Windows account and still require Hello PIN or biometric verification. They may stop working after Hello is reset, Windows is reinstalled, the account changes, or the archive is moved to another computer. Keep a password or key file recovery condition when using Hello. NingRan never stores the Hello PIN, face data, or fingerprint data in the archive.
- `.nrid`: Encrypted private identity backup.
- `.nrpub`: Shareable public identity.

## Privacy and Security Design

- An encrypted file can be renamed without affecting decryption.
- The full path of the original file is not stored in the encrypted file.
- The protection method, sender identity, original names, and internal directory structure are not shown before a successful unlock.
- Physical-device names, models, capacities, and original identifiers are not stored as plaintext in the encrypted file.
- A regular file used as a key is read only; it is not modified or converted.
- When saving to NTFS, version 8.0.2 leaves the main `.jpg` as the unchanged ordinary cover photo and stores encrypted content in its alternate data stream. Legacy `.nrenc` files remain supported.

When moving a `.jpg`, its hidden data is retained only when Windows normally moves or copies it between NTFS disks. Copying to FAT, exFAT, some cloud-sync folders, or some archive tools can lose that data. The photo will still look normal, but NingRan can no longer open its encrypted content. Before carrying, uploading, or sending it across disks, choose **Export** in NingRan and export an encrypted `.nrenc` package.

## Secure Delivery

Choose **Secure Delivery** in the main window to add multiple files and top-level folders. The wizard preserves nested folders, empty folders, empty files, and names containing Chinese, English, spaces, and common symbols. After you enter a note, password, expiry, and export rule, NingRan checks the inputs, destination, and free disk space, creates the `.nrenc`, then reopens and fully verifies it. Cancellation or failure does not modify the source material.

The recipient must install NingRan and complete password and sender verification before delivery information and the file tree are shown. When plaintext export is prohibited, single-file, folder, and full export are refused both in the interface and by the encrypted reading layer, while supported content remains viewable inside NingRan before expiry. After expiry, the name, note, sender, intended recipient, and file tree remain visible, but text, images, PDF, audio, video, and all plaintext exports stop immediately; existing reading sessions are cancelled too.

Expiry depends on the recipient computer's local clock and cannot fully resist deliberate clock changes. Export controls only limit ordinary NingRan actions and cannot prevent screenshots, photos, or screen recording. NingRan does not upload or transmit delivery packages. USB, email, chat, and cloud services may retain copies, filenames, or transfer records. Provide the password separately through a safer channel.

## Fixed-capacity vaults

New vaults can use a fixed capacity of 1 GB, 5 GB, 20 GB, 50 GB, or a custom size. Unused space is filled with random data, and adding, changing, or deleting content does not change the single vault file's total size. The new format reads its encrypted directory and required blocks directly; opening, changing a small file, and locking no longer unpack or rebuild the whole vault. Initial creation must actually write the selected capacity, so time and disk writes grow with that size; progress and cancellation remain available.

During creation, the off-by-default **Create concealed space** option assigns two clearly different passwords and two fixed regions inside the same vault. The everyday password shows only everyday content; the secret password shows only the other content. Each uses a separate data key and encrypted directory, and both unlock through the same **Open vault** entry point. Either password mounts its selected space as a temporary Windows drive and opens File Explorer. In-app browsing is offered only as a fallback if mounting fails. Total capacity and region allocation cannot be changed after creation, and a forgotten password cannot be recovered.

“Concealed” means reducing direct exposure in the everyday interface, directory, and ordinary records; it does not mean absolutely undiscoverable. Long-term comparison of vault copies, keyboard or screen monitoring, memory forensics, and records left by plaintext export, Windows, external applications, search, thumbnails, antivirus software, or cloud sync can reveal usage.

Existing legacy vaults remain readable. Inspecting a legacy single-file vault reads only its small identification entry instead of unpacking the whole file. **Upgrade legacy vault** creates a separate fixed-capacity vault and moves one encrypted block at a time without restoring the whole plaintext to disk. Success is reported only after the result is reopened and fully verified. The original is never overwritten or deleted; keep it until you have independently checked the upgraded copy. Exporting a vault to `.nrenc` reads the unlocked space directly and does not depend on a temporary drive, so export remains available when mounting fails and the in-app browser is used. Export shows overall progress across compression analysis, encrypted writing, and full verification, then adds current-stage speed and estimated time after a few seconds. After full verification, vault export skips the additional whole-package read that exists only to protect optional source deletion. The 15-minute inactivity lock is deferred only while this export is running and is checked immediately afterward. Windows lock, sign-out, sleep, authorized-device removal, manual lock, and export cancellation still stop the export immediately.

Keep passwords, key files, private-identity backups, and authorized devices in separate locations. The application cannot recover an identity password or missing unlock material.

Trusted-contact records are stored where ordinary programs cannot modify them. Adding, removing, or re-verifying a contact requires Windows administrator confirmation. Contacts retained from 6.1.11 or earlier are not trusted silently and must have their verification codes checked again. FIDO2 security keys must support a PIN or biometric verification; the application does not fall back to touch-only confirmation.

## Secure Viewing and Strict Protection

Player settings in the upper-right corner of the main window lets users choose whether content in ordinary encrypted files and secure-delivery packages opens in NingRan Player, the built-in player, or the Windows default program. The choice is saved locally and reused on the next launch; NingRan Player is the default. When selected, NingRan Encryption first recognizes the player installed under `C:\Program Files\Mier\Media-Helper` and continues to support the legacy `C:\Program Files\media-helper` location. If the player is missing or cannot establish its secure connection, NingRan explains the reason and automatically uses the built-in player. With “Open with the default program”, double-clicking any regular file exports it to a temporary folder and opens it with Windows; NingRan cleans it when the application closes. If its size or hash changed, NingRan asks for the archive and identity passwords and replaces the original entry when closing. If the default program fails, NingRan explains the reason and continues with the original in-app view or export flow. Strict Protection asks before allowing an external program to read temporary plaintext; high-security view remains in-process only. This choice does not apply to the vault fallback viewer. Enabling **Read subfolders** lists media from every level below the current folder; disabling it lists only the current level. Media is still read on demand through the encrypted session in the other modes.

Secure viewing locks the encrypted file while it is open. Timeline previews are generated by a small in-application playback surface, remain only in memory, and show a clear “Preview unavailable” state instead of waiting indefinitely when no frame can be obtained within two seconds.

Strict Protection stores its settings in a Windows area writable only by administrators and requests administrator approval for its separate monitor. It periodically checks whether any other program still holds memory-reading access to the main window, embedded player, preview surface, or monitor. When found, NingRan records the time, accessing program, protected component, and result; stops the active operation; cleans temporary content; and informs the user. To prevent an attacker from hiding inside a legitimate process, version 6.1.12 no longer provides custom or automatic allow-list entries. While the monitor is running, audio and video use the in-process player, PDF viewing is paused, and any external viewer opened before enabling protection is closed first. Logs never include video frames, file contents, passwords, or keys and can be exported by the user.

Strict Protection is a detection-and-cleanup measure, not a guarantee that access is blocked. A very short read can end before the next check. For especially sensitive content, choose **High-security open (administrator confirmation)**. It starts a separate elevated viewing window, never transfers a password or key file from the ordinary window, and requires fresh verification. That window views text and common images only: it does not load a browser or third-party playback plug-ins, so audio, video, and PDF are unavailable, and export, deletion, or modification remain disabled. This reduces how long unlock material remains in the ordinary window, but it is not Windows' highest protected-process level: software under the same Windows account that can already read other programs' memory can remain outside the app's control. Software with administrator or higher privileges, screenshots, and malicious software running at the same elevated level also remain outside its protection.

NingRan checks whether Windows exposes virtualization-based secure-area support. Passwords and the data key used during secure viewing attempt to use locked memory and are cleared immediately after use; Windows can decline a lock because of system-resource or permission limits. Unsupported computers keep the existing encryption and viewing features, with the limitation shown clearly. A normal desktop application cannot turn its whole viewer into Windows' highest protected-process level or an enclave by itself, so this status is not an absolute security boundary.

Use Strict Protection or High-security open only when appropriate, and keep Windows, security software, and backups current.

## Lossless Compression and Media Use

The encryption screen offers four levels: **Store**, **Fastest**, **Standard**, and **Complete**. Standard skips formats that are usually already compressed, such as MP4, MP3, JPG, and archive files; Complete tries every file. NingRan uses lossless Zstandard compression, compares each compressed segment with the original, and stores only the smaller one without lowering image, audio, or video quality. Before appending, it estimates the size increase and checks for identical content; an exact size report is shown after encryption or append completes.

After an encrypted media file is unlocked, the player still receives the original media bytes and the existing external media transport logic remains unchanged. Thumbnails, seeking, jumping from 0:00 to 30:00, and playback-speed changes read the needed portions on demand, but response also depends on video keyframes, codecs, disk speed, and computer performance. Playback of every media codec is not guaranteed. The **Export** button lets you choose either a portable `.nrenc` package with no plaintext created or a plaintext export.

The installer can be switched between Chinese and English. The selected language is saved beside the installed executable and is used by the help window. The separate NingRan Media Player is not bundled with the NingRan Encryption installer, and the Media-Helper integration channel does not require an upgrade.

## Installation

Windows x64 users can generate the installer with the release command below. Installation upgrades the installed program normally, so close NingRan Encryption first; older versioned installer files in `dist` are retained.

```text

```

## Build and Run

Requirements:

- Windows x64
- .NET 10 SDK
- PowerShell or Windows Terminal

Run the following commands from the repository root:

```powershell
dotnet restore NingRan.sln --locked-mode
dotnet build NingRan.sln -c Release
dotnet run --project src/NingRan.Windows/NingRan.Windows.csproj -c Release
```

After building, you can run the desktop project directly. Most users should use the installer from the release page.

To create one self-contained Windows x64 EXE installer:

```powershell
powershell -ExecutionPolicy Bypass -File build/Build-Release.ps1
```

The installer and its SHA-256 checksum are written to `dist`. Versioned filenames keep older installer packages when a new one is built. Without a code-signing certificate, Windows identifies the installer as an unknown publisher.

Release-lab acceptance for dual-space vaults on real removable media, a fully offline system, and controlled power-loss equipment starts with:

```powershell
.\build\Invoke-DualVaultHardwareAcceptance.ps1 -Scenario Removable -Action Prepare -TestRoot F:\
```

See [HARDWARE_ACCEPTANCE_PROCEDURE.md](HARDWARE_ACCEPTANCE_PROCEDURE.md) for the complete Chinese step-by-step procedure and pass criteria. The tool refuses to record an internal disk as removable-media evidence or a still-connected system as offline evidence.
